# RoutePlanning 設計書

ツーリング・ドライブの**新しい目的地・経由地**を提案するアプリケーションの設計。過去の走行実績（[MyKMLsMap](https://github.com/yzkn/MyKMLsMap) に赤線で描かれているもの）と重なりすぎない、新規開拓につながる提案をする。

- 状態: 初版（設計のみ。実装は未着手）
- 範囲: この文書は「何を・どう作るか」を決める。実装・データの取り込み・公開は別の作業で行う

## 1. 目的と、目的にしないこと

### 目的

1. 出発地と、使える時間（または距離）を入れると、**まだ走っていない道を多く通る**目的地・経由地の候補を、地図の上に挙げる
2. 候補ごとに「どれだけ新しいか（未走行の割合）」を数字で示し、選ぶ理由が分かるようにする
3. 選んだ候補で経路を作り、Google マップなどのナビに渡せる形で書き出す

### 目的にしないこと

- ターンバイターンのナビゲーション（既存のナビに任せる）
- 走行記録の取得（記録は今まで通り、別の道具で KML に書き出して MyKMLsMap に置く）
- 走行実績の公開・共有の機能

## 2. 参考にするもの: MyKMLsMap の構成（2026-11-20 に読んで確かめた事実）

| 項目 | 内容 |
|---|---|
| 実績のデータ | `kml/YYYYMM.kml`（月ごと、2021-01 から）。中身は、時刻つきの `Point`（`TimeStamp`）と、経路の `LineString`。`Folder` で 1 回の走行（名前は目的地）をまとめる |
| 変換 | GitHub Actions（`.github/workflows/kml2geojson2pbf.yml`）で、`togeojson` → `geojson-merge` → `tippecanoe`（`-z18 -Z4 -l All`、圧縮なし）で、ベクタータイル（PBF）を作り、`gh-pages` の `tiles/` に置く |
| 表示 | MapLibre GL JS。ソース `https://yzkn.github.io/MyKMLsMap/tiles/{z}/{x}/{y}.pbf`、ソースレイヤー `All` を赤い線で描く。背景は地理院地図の淡色（`js/pale.json`） |
| 逆ジオコーディング | 国土地理院の `mreversegeocoder.gsi.go.jp/reverse-geocoder/LonLatToAddress` と、市区町村コードの表（`js/geo/muni.js`） |
| タイルの取得 | `tiles/` の PBF は `Access-Control-Allow-Origin: *` で返る（z7・z12 の 1 枚ずつで確かめた）。ブラウザから直接読める |

この構成に合わせ、RoutePlanning も**静的なウェブアプリ（GitHub Pages）**を基本にする。サーバーを持たない。

## 3. 全体の構成

```
[ブラウザ（GitHub Pages の静的ページ）]
  ├─ 走行実績の読み込み … MyKMLsMap の公開タイル（PBF）／手元の KML ファイル
  ├─ 走行済みの格子（カバレッジ）を作る … ブラウザの中だけで計算・保存
  ├─ 候補地の取得 … 道の駅・峠・展望台など（静的な JSON と、必要なら Overpass API）
  ├─ 候補の採点 … 新しさ × 魅力 × 行きやすさ
  ├─ 経路の計算 … 経路探索の API（OSRM / Valhalla など。7 章）
  └─ 書き出し … Google マップの経路の URL・GPX・KML
```

### 技術の選び方（案）

| 部分 | 案 | 理由 |
|---|---|---|
| 地図 | MapLibre GL JS ＋ 地理院タイル | MyKMLsMap と同じ。実績のタイルをそのまま重ねられる |
| ベクタータイルの読み取り | `@mapbox/vector-tile` ＋ `pbf` | PBF から線の座標を取り出す |
| 格子 | スリッピーマップのタイル番号（z14）、または H3 | 追加の依存が要らないのは前者。最初は z14 のタイル番号で始める（5.1） |
| 空間の計算 | Turf.js（必要な関数だけ） | 線のバッファー・距離・線上の点 |
| ビルド | 当面は無し（素の ES Modules）。重くなったら Vite | MyKMLsMap と同じく、静的ファイルを置くだけで動く |

依存の追加は、実装の段階で個別に決める（この文書では案にとどめる）。

## 4. データ

### 4.1 走行実績（入力）

2 通りを用意し、設定で選ぶ。

| 方式 | 内容 | 長所 | 短所 |
|---|---|---|---|
| A. 公開タイル（既定） | MyKMLsMap の `tiles/{z}/{x}/{y}.pbf` を、表示範囲の分だけ z12 で読み、線を取り出す | 準備が要らない。新しい走行も CI のあとに自動で入る | 低い z では線が間引かれる（tippecanoe の単純化）。時刻・走行ごとの区切りは無い |
| B. 手元の KML | `kml/*.kml` をファイル選択で読み込む | 時刻・走行ごとの情報が使える（「最近走っていない」なども判定できる） | 読み込みの手間。全量で 120 MB 程度あり、ブラウザで読むには重い（5.1 で格子にしてから保存する） |

**リポジトリには実績のデータを置かない。** 計算した格子も、ブラウザの中（IndexedDB）にだけ保存する（9 章）。

### 4.2 候補地（入力）

| 種類 | 出典の案 | 備考 |
|---|---|---|
| 道の駅 | [国土数値情報 道の駅データ（P35）](https://nlftp.mlit.go.jp/ksj/gml/datalist/KsjTmplt-P35.html) | 全国を網羅。ビルド時に GeoJSON に変換して同梱する案。**利用条件（出典の表示など）は要確認** |
| 峠・展望台・滝・ダム・灯台・温泉など | OpenStreetMap（[Overpass API](https://wiki.openstreetmap.org/wiki/Overpass_API)） | 例: `mountain_pass=yes`、`tourism=viewpoint`、`waterway=waterfall`、`man_made=lighthouse`。タグの選び方は実装で詰める。データは ODbL（出典の表示が要る）。公開のサーバーへの負荷に配慮し、ビルド時に地域ごとに取って同梱するのを基本にする |
| 利用者が足す場所 | 手で登録（名前・位置・メモ） | ブラウザの中だけに保存 |

### 4.3 道路（経路の計算）

経路探索の API に任せる（7 章）。道路網そのものは持たない。

## 5. 提案の方法

### 5.1 走行済みの格子（カバレッジ）

1. 実績の線を、一定の間隔（例: 100 m）で点に分ける
2. 各点を **z14 のタイル番号**（1 辺はおよそ 2 km 弱。北緯 35 度付近）に割り当て、「走行済みの格子」の集合にする
3. 経路の「重なり」は、より細かく見る: 経路の線から一定の幅（既定 50 m）以内に実績の線があるかで判定する（5.3）。格子は、候補を粗く絞るのに使う

格子の大きさ・幅は設定で変えられるようにし、実際に使って調整する（**既定値は推測。実地で確かめる**）。

### 5.2 候補の採点

候補地 `p` ごとに、次を掛け合わせた点数で並べる。

| 要素 | 内容 | 計算の案 |
|---|---|---|
| 新しさ `N(p)` | 候補のまわりに、走行済みの格子がどれだけ少ないか | 半径 r（既定 5 km）内の格子のうち、未走行の割合 |
| 魅力 `A(p)` | 種類ごとの重み | 例: 峠 1.0、展望台 0.9、道の駅 0.7。利用者が変えられる |
| 行きやすさ `F(p)` | 使える時間・距離に収まるか | 出発地からの直線距離 × 道路の係数（既定 1.4）で、往復が予算の範囲に入るものだけ。範囲の端に近いほど少し下げる |

`score(p) = N(p)^α × A(p) × F(p)`（`α` は新しさをどれだけ重く見るか。既定 1.0）

直線距離で絞った上位の候補（例: 20 件）だけ、実際の経路を計算し（5.3）、点数を付け直す。経路探索の API を呼ぶ回数を抑えるため。

### 5.3 経路の新しさ（未走行の割合）

経路（出発地 → 経由地 → 目的地 → 出発地）について:

- **未走行の割合** = 経路のうち、実績の線から幅 50 m の外にある区間の長さ ÷ 経路の全長
- 行きと帰りで同じ道を通る経路は、新しさが半分になる。帰りは別の道になるよう、帰りの経由地を 1 つ足す候補も作る（5.4）

「重複しすぎない」の目安として、**未走行の割合が既定 60 % 以上**の経路を「新規開拓」として示す（閾値は設定で変える。既定値は推測）。

### 5.4 経由地の提案（周回ルート）

目的地を 1 つ選んだあと、未走行の割合を上げる経由地を足す。

1. 行きの経路と帰りの経路が重なる区間を見つける
2. 重なる区間の近く（左右数 km）にある、未走行の格子の中の候補地を探す
3. 経由地を足したときの「未走行の距離の増え方 ÷ 所要時間の増え方」が大きいものから、予算に収まる範囲で足す（貪欲法。経由地は既定で最大 3 つ）

最適な巡回（巡回セールスマン問題）は解かない。候補が少ないので、貪欲法で足りると見込む（**推測。実装後に結果を見て判断**）。

## 6. 画面

1 画面の地図アプリ（スマートフォンでも使える）。

| 部分 | 内容 |
|---|---|
| 地図 | 背景（地理院の淡色）＋ 実績の赤線（MyKMLsMap と同じ見た目）＋ 未走行の格子のうすい塗り（切り替え可） |
| 条件のパネル | 出発地（地図で指す・現在地・保存した地点）、予算（時間 または 距離）、往復 / 片道、候補の種類、重みの調整 |
| 候補の一覧 | 点数の順。名前・種類・距離・所要時間・未走行の割合。押すと地図で経路を表示 |
| 経路の詳細 | 経由地の並べ替え・削除・追加、未走行の区間を別の色で表示 |
| 書き出し | Google マップの経路の URL（経由地つき）、GPX、KML |

## 7. 経路探索の API（要確認）

| 候補 | 内容 | 注意 |
|---|---|---|
| OSRM の公開デモ | `router.project-osrm.org` | [デモサーバーの説明](https://github.com/Project-OSRM/osrm-backend/wiki/Demo-server)では、上限は 1 秒に 1 リクエスト、稼働の保証は無い。**試作の間だけ** |
| Valhalla・GraphHopper などの提供サービス | 外部の有料・無料枠のサービス | 費用・利用規約・API キーの扱い（静的ページに置けない）を、実装の前に確かめる |
| 自前の OSRM / Valhalla | 日本の OSM データで立てる | サーバーが要る（費用が生じる）。必要になったときに検討 |

最初は OSRM の公開デモで試作し、経路の API を差し替えられるように、呼び出しを 1 か所（`routing` のモジュール）にまとめる。

## 8. 段階（実装の順）

| 段階 | 内容 | 終わりの条件 |
|---|---|---|
| M1 | 地図に、MyKMLsMap の実績の赤線を重ねて表示する | MyKMLsMap と同じ線が出る |
| M2 | 公開タイルから走行済みの格子を作り、未走行の格子を塗る | 表示範囲の格子が数秒で出る |
| M3 | 道の駅のデータで候補を採点し、一覧に出す（直線距離のみ） | 出発地と予算から候補が並ぶ |
| M4 | 経路探索の API で経路を作り、未走行の割合を出す | 候補ごとに割合が出る |
| M5 | 経由地の提案（5.4）と書き出し | Google マップで経路が開ける |
| M6 | 手元の KML の読み込み（方式 B）、OSM の候補地 | 任意 |

## 9. 個人情報の扱い

- リポジトリは公開。**走行実績の座標、自宅・出発地の位置、走行の日時を、リポジトリ（コード・試験のデータ・文書・Issue）に入れない**
- 出発地・計算した格子・利用者が足した場所は、ブラウザの中（IndexedDB / localStorage）にだけ保存する。外部に送るのは、経路の計算に要る座標（経路探索の API へ）と、地図のタイルの取得だけ
- 試験のデータは、架空の線・点で作る
- 書き出した GPX・KML・URL には出発地が入る。共有するときは利用者が判断する（画面に注意を出す）

## 11. 確かめていないこと

- 提案の良し悪し（実際に走っての評価）
- 外部の API（経路探索・Overpass・地理院）の提供元の挙動・上限・規約の細部
- 公開タイルの線の間引き（tippecanoe の単純化）が、z12 で重なりの判定にどれだけ影響するか
- 既定値（格子・幅・閾値・道路の係数）の妥当さ
